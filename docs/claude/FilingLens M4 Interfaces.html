Where the 12.5 seconds go

I streamed the PepsiCo EBITDA question through the real agent and timed every node. This chart decides most of M4's design.

  • 99.8% of the time is LLM calls. Our database and Python code take about 25 ms in total. Making the API layer faster won't help; showing progress will.
  • Seven moments when something happened. These are the events /ask/stream sends, so the user sees work after 1.2 s instead of a blank screen for 12.5 s.
  • Model clients cost 1,251 ms to create; building the agent from them costs 7 ms. So the server creates the clients once at start-up and builds the agent per request (concept 6).
Eight concepts, in build order

Each one: what it is, why it was invented, why we need it, how we build it, and our data

You know FastAPI and HTTP well, so these cards skip the basics and focus on what changes when the thing behind the API is a slow, non-deterministic, paid LLM agent.

1

An API contract for an LLM app

What it is

The same thing you've built many times: typed request and response models, validated at the edge. What's new is what the response must carry. An LLM answer is only useful if the caller can check it, so the contract includes the evidence (sources with URLs), the agent's trace (tool calls, rounds), its own quality flag (verified), the outcome (answered / not found / refused), and IDs to find the request again.

Backend analogy: a payment API returns not only “ok” but a transaction ID, status and receipt. An LLM API returns the answer plus its receipt: where each number came from.

Why it exists

Early LLM demos returned a bare string. Nobody downstream could tell a sourced number from a guess, retry safely, or debug a bad answer.

Well-known exampleOpenAI's and Anthropic's own APIs return far more than text: a request ID, the stop reason, token usage, tool calls as structured JSON. Perplexity returns its citations as a separate list next to the answer, which is the pattern we follow.
Why FilingLens needs it

CLAUDE.md: “Every answer returns sources (filing URL + section) and the Langfuse trace ID.” The M3 AgentResult already has almost everything; the API exposes it as a stable schema.

How we build it
class AskRequest(BaseModel):
    question: str = Field(min_length=3, max_length=2000)   # a length cap is also a cost cap

class AskResponse(BaseModel):
    request_id: str                 # to find this request in logs
    answer: str
    outcome: Literal["answered", "not_found", "refused"]
    verified: bool                  # passed the M3 grounding check
    sources: list[SourceOut]        # n, kind, label, url: only the cited ones
    tool_calls: list[ToolCallOut]
    rounds: int
    latency_ms: int
    trace_id: str | None = None     # Langfuse, filled from M6; in the schema now so it won't break clients
On our data

For PepsiCo, sources would hold [1] XBRL · PEP FY2022 revenue with the SEC filing-index URL of accession 0000077476-23-000007, and [4] calculate. A UI can render those as links without parsing the answer text.

2

A synchronous agent in an async server

What it is

FastAPI runs on an event loop. An async def endpoint must never block it. Our agent is synchronous: sync SQLAlchemy sessions and sync llm.invoke() calls that wait up to 8 seconds. FastAPI's rule: a plain def endpoint runs in a threadpool (40 threads by default), so blocking there is fine.

Backend analogy: exactly what you'd do with a blocking driver in an ASGI app, or a sync Celery task: run it on a worker thread and keep the loop free.

Why it exists

Python web servers moved from WSGI (one thread per request) to ASGI (one event loop, many requests) for long-lived connections like websockets and streaming. Mixing in blocking code is the classic mistake: one slow call freezes every request on that loop.

Well-known exampleDjango added async views in 3.1 but still runs sync views in a threadpool through sync_to_async. Starlette and FastAPI do the same for plain def routes.
Why FilingLens needs it

An answer takes 2–30 seconds. With an async def route calling our sync agent, a second user would wait for the first one to finish.

Trade-off: 40 threads means about 40 concurrent questions per process, which is plenty for a demo. The fully async alternative (ainvoke, async psycopg sessions) scales further but means rewriting the tools and the session handling. That's not worth it at this scale; it's recorded in ADR-010 as the upgrade path.

How we build it
@app.post("/ask", response_model=AskResponse)
def ask(body: AskRequest, agent = Depends(get_agent)):   # def, not async def: runs in the threadpool
    return to_response(run_agent(agent, body.question))
On our data

The PepsiCo request spends 12.47 of its 12.49 seconds waiting on OpenAI and Anthropic. In a thread, that waiting costs nothing to other requests.

3

Streaming with Server-Sent Events (SSE)

What it is

One normal HTTP response that stays open. The server writes small text blocks to it as things happen: event: step, then a data: {...} line, then a blank line. The client reads them one by one. The connection is one-way (server → client), and the stream is plain text over plain HTTP.

Backend analogy: tail -f over HTTP. Or a chunked download where each chunk is a JSON event.

Why it exists

Before SSE, live pages polled (“anything new?” every second) or used long-polling hacks. SSE was standardised with HTML5 (the browser's EventSource) for exactly this case: the server pushes updates, the client only listens. Websockets are two-way and need their own protocol upgrade, which is more than a progress feed needs.

Well-known exampleChatGPT's text appearing word by word. With stream=true, the OpenAI and Anthropic APIs send SSE events, one per chunk of text. Every streaming chatbot you've used is SSE underneath.
Why FilingLens needs it

The brief's target is an answer in under 30 seconds, and the mean is 13.9 s. A blank screen for 14 s feels broken. Seeing “Fetching XBRL: PEP FY2022 revenue, operating income, D&A” after 4.8 s shows the work and builds trust.

How we build it
def events(agent, question):                       # a sync generator: Starlette iterates it in a thread
    for update in agent.stream(state, stream_mode="updates"):
        yield sse("step", describe(update))          # "event: step\ndata: {...}\n\n"
    yield sse("result", final_response)

@app.post("/ask/stream")
def ask_stream(body: AskRequest, agent = Depends(get_agent)):
    return StreamingResponse(events(agent, body.question), media_type="text/event-stream")

No extra library: Starlette's StreamingResponse is enough. sse-starlette adds keep-alive pings and disconnect handling; we can add it if we need them. We use POST rather than the browser's GET-only EventSource, because the question goes in a JSON body. Our client is Python, so that doesn't matter.

On our data

The PepsiCo run would send 7 step events at 1.2, 4.8, 4.8, 6.5, 6.5, 8.6 and 12.5 s, then one result. Play it in Watch a request.

4

Streaming steps, not tokens

What it is

LangGraph can stream at different levels. stream_mode="updates" yields one item per finished node, with what that node changed. "messages" yields LLM tokens as they're generated. "values" yields the whole state after each step. You can ask for several at once.

Why it exists

Chatbots streamed tokens because they had one long LLM call. Agents spend most of their time in many shorter calls and tools, so “which step am I on?” became the more useful signal.

Well-known examplePerplexity and ChatGPT's search show “Searching… Reading 6 sources…” before the answer text starts. Claude Code shows each tool call as it runs. Both are step streams, with tokens only for the final text.
Why FilingLens needs it

Our answer goes through a check, and in M3 the check could send it back for one rewrite. If we streamed the first draft's tokens, the user could watch numbers appear that the check then rejects. So we stream steps live and send the answer when it's checked. The answer call is 3.9 of the 12.5 s; streaming its tokens is a possible later improvement.

How we build it
for mode, chunk in agent.stream(state, stream_mode=["updates", "values"]):
    if mode == "updates":                 # {"plan": {"messages": [AIMessage(tool_calls=...)], "rounds": 1}}
        yield step_event(chunk)
    else:
        final_state = chunk                   # the last "values" is the full final state → AskResponse

5

OpenAPI and Swagger docs

What it is

OpenAPI is a JSON document that describes every endpoint: paths, methods, request and response schemas, status codes and examples. FastAPI writes it for you from the Pydantic models (/openapi.json) and serves two UIs on top of it: Swagger UI at /docs, where you can click “Try it out”, and ReDoc at /redoc.

Why it exists

API docs used to be hand-written wiki pages that drifted from the code. Swagger, created in 2011 for the Wordnik dictionary API, made the description machine-readable. In 2015 it was donated to the new OpenAPI Initiative under the Linux Foundation, and the spec was renamed OpenAPI. From one file you get docs, client generators and contract tests.

Well-known exampleStripe and GitHub publish their APIs as OpenAPI specs, and their SDKs are generated from them.
Why FilingLens needs it

The demo audience (interviewers, the fictional analyst team) can explore the API without reading code. And there's a nice link to M3: tool schemas are the same idea. The JSON Schema that bind_tools sends the LLM for get_financials is the same format OpenAPI uses for AskRequest. Both are a contract for a client: in M3 the client is an LLM, in M4 it's a person or a program.

How we build it

Mostly for free. We add a title, a version, an example on AskRequest (the PepsiCo question), and document the text/event-stream response of /ask/stream, which FastAPI can't infer. After M4, the follow-up page (M4.2) will embed this real Swagger UI.

On our data

“Try it out” on /ask with the prefilled PepsiCo example returns the 16.5% answer and its sources, the same JSON the UI renders.

What to create once, and what per request

What it is

A server has two lifetimes. App lifetime: things created at start-up and shared, such as model clients with their HTTP connection pools, and the settings. Request lifetime: things that must not be shared between concurrent requests, such as a database session. FastAPI's lifespan handles the first, and Depends() generators handle the second.

Backend analogy: the SQLAlchemy engine is per app and the session is per request. You already do this. The only new part is deciding which side the LLM pieces fall on.

Why it exists

Creating expensive things per request wastes time; sharing stateful things across requests causes bugs that only appear under load.

Well-known exampleThe OpenAI and Anthropic SDK docs recommend creating the client once and reusing it, because each client holds a connection pool. Creating one per request is a common cause of slow LLM apps.
Why FilingLens needs it

Our tools are bound to a session: make_tools(session, embedder). So the agent can't be global, or two requests would share one DB session across threads. And it can't be fully rebuilt per request, or we'd pay 1.25 s for model clients each time.

How we build it
@asynccontextmanager
async def lifespan(app):
    app.state.models = Models(llm=get_chat_model(), guard=get_router_model(), embedder=get_embeddings())
    yield                                                       # once: 1,251 ms

def get_agent(request: Request, session = Depends(get_db)):   # per request: 7 ms
    m = request.app.state.models
    return build_agent(m.llm, m.guard, make_tools(session, m.embedder), available_filings(session))

Streamlit as a thin demo client

What it is

A Python library that turns a script into a web app. Each widget is a function call (st.chat_input, st.status, st.expander), and the script re-runs top to bottom on every interaction. No HTML, CSS or JavaScript.

Backend analogy: like Django admin: not what you'd build a consumer product with, but a working UI in an afternoon.

Why it exists

Data scientists had models but no front-end skills. Every demo meant waiting for a web team. Streamlit launched in 2019 to close that gap, and Snowflake bought it in 2022. Gradio fills the same niche, with Hugging Face Spaces as its well-known home.

Well-known exampleMost LLM demo apps on GitHub and Hugging Face Spaces are Streamlit or Gradio. Streamlit's st.chat_message and st.status were added specifically for chatbots and agents.
Why FilingLens needs it

A 2-minute demo needs a screen, not curl. The key design rule: the UI only talks to the API, never to the agent directly. It's a thin client, so it proves the API works, and a React front end could replace it without touching the backend.

How we build it
question = st.chat_input("Ask about a 10-K…")
with st.status("Working…") as status:
    for event in client.ask_stream(question):     # filinglens.api.client: httpx + SSE parsing
        if event.type == "step": status.write(event.label)
        else: result = event.data
st.markdown(result.answer); show_sources(result.sources)
On our data

Example buttons for three real questions (PepsiCo EBITDA, Boeing legal battles, “Should I buy AMD?”), so the demo shows a number answer, a text answer and a refusal in under a minute.

Failure modes and tests for an LLM endpoint

What it is

Deciding in advance what the API says when each dependency fails, and testing all of it without calling a real model.

FailureResponseWhy that code
Question empty or over 2,000 characters422The client's fault; Pydantic does it
OpenAI or Anthropic error or timeout502 “model provider error”An upstream service failed, not our code
Postgres down503, and /health says soTemporarily unavailable; a load balancer can retry elsewhere
Failure mid-streaman event: errorThe 200 status is already sent, so the error must travel as an event
“Should I buy AMD?”200, outcome refusedA refusal is a correct answer, not an error
Why it exists

LLM providers have outages and rate limits more often than databases do, and an agent depends on two of them plus Postgres. Without explicit mapping, every failure becomes a 500 and nobody knows whose fault it was.

Well-known exampleOpenAI's status page has regular incidents, and Anthropic's API returns 529 overloaded under load. Production LLM apps handle these as normal events, with clear errors, retries and fallbacks.
Why FilingLens needs it

A demo that crashes with a traceback when an API key is wrong is worse than no demo. And CI can't call real models, because of cost, keys and non-determinism.

How we build it

FastAPI's app.dependency_overrides[get_agent] swaps in the M3 test agent built from the scripted FakeLLM. So the API tests run the real graph, real tools (calculate) and real SSE encoding, with fake model replies, in milliseconds. The client is tested with httpx.MockTransport, and the UI with Streamlit's AppTest.

On our data

The M3 test “AMD quick ratio, two rounds, then a cited answer” becomes an API test: POST /ask → 200, verified: true, sources [1] and [5] with SEC URLs. The same script through /ask/stream must emit guard → plan → tools → plan → tools → plan → answer → check, then the result.

Practice

Interview questions on M4

Your agent takes 14 seconds. How do you serve it over HTTP without blocking other users?

The agent is synchronous, so the endpoint is a plain def and FastAPI runs it in a threadpool; the event loop stays free. Each request gets its own DB session and agent instance; model clients are shared because they're thread-safe and expensive to create (1.25 s for us vs 7 ms per agent). For more scale: an async agent with ainvoke and async DB sessions, or a job queue with Celery and polling for very long tasks.

SSE or websockets for streaming agent progress?

SSE: the data flows one way (server → client), it's plain HTTP so proxies and load balancers handle it, and it's what the OpenAI and Anthropic APIs use. Websockets are for two-way, long-lived sessions such as collaborative editing or voice. One SSE caveat: the browser's EventSource only does GET, so with a POST body you read the stream with fetch or httpx.

Why stream agent steps instead of tokens?

Most of an agent's time is in several shorter LLM calls and tools, not one long generation, so “what is it doing now” is the useful signal. And our answer passes a grounding check that may reject the first draft; streaming draft tokens would show numbers that get withdrawn. Steps live, final text once checked. Token streaming for the final answer is a later option.

How do you test an API whose core is an LLM?

Swap the agent dependency for one built on a scripted fake LLM (dependency_overrides), so tests exercise the real graph, tools, schemas and SSE encoding without network calls. Test the error mapping by making the fake raise. Keep real-model checks in the eval, which runs separately and is versioned.

What status code for “Should I buy AMD?”

200 with outcome: "refused". The system worked correctly; a refusal is a valid answer. Errors are for failures: 422 bad input, 502 when the model provider fails, 503 when the database is down.

An error happens after you've started streaming. What does the client get?

The 200 status and headers are already sent, so you can't change the status. You send an event: error with a message, and the client must handle it. That's why the event types (step, result, error) are part of the documented contract.

Why have a separate Python client if Streamlit could call the agent directly?

So the UI proves the API works and stays replaceable. The client holds the HTTP and SSE parsing in one tested place. Any other consumer (a notebook, a Slack bot, an MCP server) reuses it, and the UI has no access to the database or keys.

What would you add before putting this on the internet?

Authentication and per-key rate limits (each request costs money), request timeouts and a max concurrency, CORS rules if a browser front end calls it, tracing (Langfuse) and structured logs with the request ID, input size caps (already 2,000 characters), and a health check wired to the orchestrator.
