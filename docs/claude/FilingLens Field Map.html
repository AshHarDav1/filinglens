The goal

Two to four hours of an analyst's day, in under thirty seconds

An equity analyst opens a 10-K, hunts for the revenue line, hunts for the paragraph where management explains it, and writes it up. We want to ask one question and get back the exact figure, management's own explanation, and a link to the page it came from — so the answer can be checked, not trusted.

01Question"What drove AMD's FY22 revenue?"
02Pick the filingticker + fiscal year
03Find paragraphssearch the filing's text
04Hand to the modelquestion + the excerpts
05Answergrounded in those excerpts
06Citationfiling URL + section

That is the whole product in six moves. Today steps 02–06 exist as code and pass unit tests, but no real filing has ever gone through them.

The one rule that shapes everything

Numbers and words come from different places

A language model reading a financial table will sometimes get a digit wrong, and a wrong digit in equity research is worse than no answer. So the system never lets the model read numbers out of text. Figures come from the SEC's structured data; the model only ever explains.

Exact figures — XBRL

Every US filing ships machine-readable tagged financials. We load them into a table and query them with SQL. No model involved, so no room for a hallucinated digit.

Revenues FY2022 = 23,601,000,000
Explanations — retrieval

The "why" only exists in prose: Risk Factors, MD&A. We search that prose for the relevant paragraphs and let the model summarise them — and only them.

"...driven by a 64% increase in Data Center..."

This is ADR-002 in the project docs. It is also the single sentence worth memorising for an interview about this codebase.

Concept · ingestion

A 300-page filing becomes a few hundred searchable pieces

You cannot hand a whole 10-K to a model — it does not fit, and most of it is irrelevant. So the filing is cut into overlapping windows of about 2,000 characters (roughly half a page each), and every window is turned into a list of 1,536 numbers called an embedding: a position in meaning-space, where passages about the same topic land near each other.

→
→

10-K HTML → overlapping 2,000-character chunks (200 of them shared with the neighbour, so a sentence is never cut in half) → one embedding per chunk, stored in Postgres next to the text.

The overlap is the detail people miss: without it, the one sentence you need can land exactly on a cut line and appear in neither piece. Each embedding is cached by a hash of its text, so re-running ingestion never pays for the same vector twice.

Concept · retrieval

Search by meaning, fenced in by company and year

The question gets an embedding too. Finding the right paragraphs is then just geometry: take the six chunks whose vectors sit closest to the question's. No keyword has to match — "what drove revenue" finds "the increase was primarily due to" without sharing a word.

Dashed fence = the SQL filter on ticker and fiscal year, applied before the distance ranking.

The fence matters more than it looks. Similarity search always returns something — ask about AMD with no filter and you can get Microsoft's paragraphs back, confidently cited. Filtering to one company's one filing first is what stops that.

The decision this week

Two runs, one comparison

First the model answers all 20 questions from memory alone. Then it answers them again with retrieved excerpts. The gap between those two numbers is the only evidence that retrieval is doing anything — and it is the number that goes on the README.
